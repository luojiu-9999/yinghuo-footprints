# 萤火足迹 · 产品方向补充（2026-10-24）

状态（2026-10-26 更新）：本轮网页已实现原图本地保存/下载、新备份与救援、浅/深外观、萤火旅线、两种照片地图拼贴。Android/iOS 原生封装、原生文件系统适配器和真机验证，以及云端存储仍未完成。本文件覆盖此前的“三套主题全部保留”决定；当前实现与限制见 README 和 qa/features/acceptance.md。

## 1. Android / iOS 与本地原图

### 用户已明确

- 网页验证后封装为 App，需要同时考虑 Android 与 iOS。
- 照片现阶段保存在设备本地，未来有自己的服务器后再接入云存储。
- 必须支持高清原图导入，以及原图导出/下载；不以压缩图替代原图。

### 实现约束

- 分离旅行记录与照片实体，以 photoId 引用。照片实体区分原文件、显示预览和缩略图，记录文件名、MIME、字节数、尺寸、内容校验值及存储位置。原文件是实际选入应用的文件，不承诺恢复来源应用已经压缩过的相机原片。
- 原图导入后不缩放、不重新编码；缩略图和预览独立生成，用于列表、地图填充与动画。导出原图保持字节一致，可用内容哈希验证，不把 canvas 导出的 JPEG 称为原图。
- 网页和未来原生壳共享业务规则，但采用各自的持久化存储适配；原生 App 需把文件可靠复制到应用管理的持久目录，不只保留可能失效的相册临时引用。网页仍须明确站点存储空间、被清理风险和备份责任，不能承诺等同系统相册的永久保存。
- 在选择文件、原图读取、预览解码和导出到相册/文件等环节，分别验证 Android / iOS 权限、取消、失败及空间不足处理。HEIC 等来源文件应保留原文件，预览解码支持情况单独验证，不能为生成预览而覆盖原图。
- 提供本地照片存储接口和将来的云适配接口；记录稳定 ID 不随存储位置改变。未来云迁移应由用户明确开启，检查上传完成和文件校验后才决定是否释放本地副本，默认不自动删除本地原图。
- 原图可能包含拍摄位置等元信息，默认私人保存。未来公开分享须明确隐私策略，分享衍生图与私人原图分开处理。
- 原图备份不能继续无限堆入单个 Base64 JSON。需结合已有备份可靠性问题，设计兼容旧版、带清单与校验的分包或文件归档方案；任何限制都须在保存/导出前可见，并保留实际可恢复路径。

### 当前版本差距

原型旧版仅保存1100像素压缩图；2026-10-26起，新导入照片独立保存原文件，并生成最长边1600像素的衍生预览，通过 photo:ID 引用。已有旧版照片继续兼容，无法恢复已经丢弃的原片；重新选择原图也不能导致旧游记被删除。网页使用IndexedDB；原生文件系统适配器、双平台系统相册与真机验证仍待后续封装。

## 2. 一套视觉系统，两种外观

- 撤回此前三套设计主题并行的要求：统一布局、组件、字体和品牌强调色，仅保留白色浅色 / 暗夜深色两种外观。
- 两种外观不分别拥有数据、功能或导航；照片、点亮状态和回忆录共享。
- 建议保留低饱和自然色与萤火光效作品牌特征，非要求整页只能出现一种颜色；信息状态和可读性仍需区分。
- 已映射旧主题偏好且不重置数据：原 night 对应深色，其余对应浅色。原设计资产与历史截图保留作为证据。
- 当前网页仅有白色/暗夜两种外观。

## 3. 回忆录：萤火旅线（暂定名）

### 用户已明确

在回忆录里按时间把去过的地方串联，形成发光连线，由萤火虫沿线飞行，展示从一个地方到另一个地方的经历。

### 建议交互与数据规则

- 增加地图播放视图，与年度报告、旅行故事、电子相册并列；选择年度或一次已明确分组的旅行后播放，不改变原记录。
- 以“到访记录”生成节点，而非去重后的城市列表。同一城市多次到访保留，支持 A → B → A；仅手动点亮、没有明确行程时间和顺序的地区不自动编造路线。
- 按真实到访日期排序，同一天顺序不明时允许用户调整，不能把数据库读取顺序当作实际出行顺序。时间精度和顺序规则需在开发时明确。
- 年度视图表示“年度回忆串联”，不是默认认为这一年的独立旅程属于同一趟旅行；单次旅行需要明确分组与序号。初版可先用城市节点，不因现有区县多选框的排列推断游览先后。
- 路线为节点间的视觉连线，不宣称真实 GPS 轨迹、行驶路线、交通方式、路程或耗时。
- 播放时萤火虫移动、已走过的线保留光迹，到站可显示城市、日期与照片。建议支持暂停、重播、进度和速度；在减少动态效果设置下提供静态连线或低动态版本。
- 帧渲染只使用预览/缩略图，按需解码，不把所有原图同时放进内存。地图和照片都能在本地正常使用时，动画也应支持离线。
- 暂不把视频生成、音乐、公开分享或真实轨迹采集当作已授权或已实现的功能。

## 4. 照片地图拼贴

### 用户已明确

允许把图片填充到地区、省或市的范围内，拼接成一张照片地图。

2026-10-25 确认：两种方式都需要支持，由用户选择：每个区域放一张照片，多个区域拼成地图；或一个区域内部使用多张照片拼贴。多图方式属于已确认范围，不再只是后续备选。

### 建议交互与数据规则

- 单图填充模式：每个选定区域选择一张封面照片，按真实区域边界裁切；多个区域各自展示照片，组合成整张照片地图。
- 多图拼贴模式：在一个区域内部选择多张照片进行拼贴，拼贴整体裁切在该区域的真实边界内。具体模板和照片数量上限在实现前根据手机预览与内存测试确定，不擅自承诺无限数量。
- 两种模式由用户选择，按区域保存模式、照片选择、排列及裁切参数。切换时保留另一模式的编辑配置，不清空已选照片或修改原图。
- 支持省 / 市 / 区县显示层级切换，分层保存照片与区域的对应关系。全国省级拼贴、省内市级拼贴、城市内区县级拼贴都基于已有真实边界；缺失边界时明确提示，不能用虚构轮廓填补。
- 支持照片平移、缩放和裁切预览，调整参数单独保存，原图不变。提供正常点亮地图 / 照片地图切换，未填照片的区域仍可识别。
- 照片填充是展示创作，不自动制造到访记录或改变点亮、城市数和旅行统计；照片分配不能证明用户实际到访。
- 同层级按区域分别裁切；跨层级先用当前选择的显示层级，避免省照片和市/县照片互相叠盖。一个区域多次到访时由用户选封面，不静默覆盖。
- 建议支持保存拼贴布局并导出高清成品图。成品是新渲染的合成图，与“下载原图”严格区分；分辨率上限和分块渲染需根据手机内存测试确定，不能承诺无限分辨率。
- 对外导出时保留必要的地图来源标识；正式发布前应核实地图数据及对外展示/导出的适用要求，不在原型阶段宣称已符合正式商用地图要求。

## 5. 开发衔接与验收

- 已处理四项可靠性缺陷：保存/恢复共用校验；新版原图备份避开旧100MiB JSON总文件截断；启动错误提供救援；地区关系使用本地索引校验。旧版大JSON仍需保全原文件后专门迁移；新备份不承诺无限容量，32MiB清单有保守写入前保护。
- 原图存储、记录/照片分离、可恢复备份和存储适配应作为一组基础工作，避免先扩大照片容量再继续依赖单文件 100MiB JSON。
- 外观精简不应丢失任何旅行或照片。动画和拼贴在稳定的数据接口上开发，不依赖原图内嵌到记录的旧格式。
- 原图验收：选入文件与导出文件字节哈希一致；预览和裁切不改原文件；离线和重启后可读取；空间不足/权限拒绝不留下半份记录；旧照片继续可浏览。
- 动画验收：节点日期和顺序正确、重复到访不丢、同日可调整、独立旅行不冒充一趟行程、暂停/减少动态可用。
- 拼贴验收：单图填充和区域内多图拼贴均可选择；切换模式不丢编辑配置；照片不越过真实区域边界、层级切换不覆盖配置、裁切可恢复且不损原图、空白区域可见、成品清晰度与移动端内存经过验证。
- Android 和 iOS 的原生行为必须以后续真实设备测试确认；当前 Windows 网页测试不能替代双平台验收。
